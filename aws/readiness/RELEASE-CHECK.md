# Consolidated AWS check, real trading disabled

The self-contained public/iom-release-check.py runs with sudo on the existing AWS host. It reports all results together rather than requiring separate terminal commands. It verifies the current FYERS profile/owner and read access, identifies App ID type, calls the deployed signed simulation-only Core/Scalp exit/replay check, and audits the existing SQLite journal as the mentor user. It does not install/start a live execution service, change credentials, edit nginx or place/cancel/modify orders.

Journal maintenance uses the existing daily.lock to avoid overlapping the timer. It performs SQLite integrity and verified backup checks, exports only existing pending saved records, and acknowledges each only after Google accepts it. It replays the latest existing closed record twice with its deterministic event ID, then checks the complete Sheet history contains exactly one matching row. No fake trade or event is inserted in production. Truncated history over 1,000 trades, existing duplicates, gateway failures or remaining backlog fail verification; the checker never deletes records to manufacture success. Backup metadata and successful export acknowledgements are the only production SQLite writes. Existing service states/PIDs are compared before/after.

The account ID suffix -100 means non-trading. Successful authenticated reads cannot establish trading permission or static-IP registration. The report explicitly retains blockers for an unreleased real execution host, live WebSocket exit proof and actual broker order/stop proof. This checker is not real-money activation. It also cannot configure the user’s trading app or provide a trading token. Those account-side prerequisites must be completed without replacing paper credentials.

The Sheets gateway hotfix canonicalises the signed public maintenance path across Netlify’s internal function rewrite. Both exact allowed paths share nonce handling; other paths, changed bodies and incorrect signatures remain rejected. Private-safe fixed error categories distinguish gateway authentication, Google HTTP failures, login HTML and rejected Apps Script actions. The actual deployed failure must still be verified from AWS using the check; the routing test alone does not prove the production export failure has been resolved.
